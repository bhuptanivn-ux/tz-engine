# TZ Engine — Master Reference (for continuing in a new conversation)

**Purpose:** A from-scratch Python state-machine engine (`tz_engine_v9.py`) implementing a proprietary 37-event trading rule book. Input: daily OHLC (DATE, OPEN, HIGH, LOW, CLOSE). Output: an EVENT column per date. End goal: a website that recalculates events daily across ~5000 stocks × 4 timeframes (daily/weekly/monthly/yearly), via a batch pipeline (precompute → store → serve), not live per-request computation.

**Validation datasets so far** (all must be re-verified — full diff, zero unexpected changes — after any future code change):
- `new_green_test.xlsx` — 181 days, Jan–Jun 2025. **NOT currently zero-diff**: 10 diffs against its last-approved baseline (down from 42 once the §11 "weak-rule doesn't apply while dormant" fix landed — NOT a `bar_high_pool` sync, which was tried, found wrong, and reverted) — 15/05 individually confirmed correct (`NEW TZ BUY(B)`) by the user; the remaining 20/06–30/06 region (A's REAR genuinely reactivating later) not yet individually re-verified.
- `test_input3.xlsx` — 156 days. Zero diff, confirmed clean against every fix through §11/§5a.
- `new_dataset_2024_full3.xlsx` — 2024 data, extended to 10/06/2024. **NOT currently zero-diff**: 18 diffs against its last-approved baseline — 23/05 (`REAR RE-ENTER(A)`) individually confirmed correct by the user; the remaining region not yet individually re-verified. Additionally, §1a (reference-high inheritance, below) shifted `TZ BUY(A)` from 30/01 → 31/01 and added `TZ GREEN HH(B)` on 30/01 — confirmed correct by the user.
- `new_dataset_2022_full4.xlsx` — 2022 data, extended to 07/07/2022 (supersedes `new_dataset_2022_full3.xlsx`; the one that surfaced the `red2_ever` reactivation bug, the §5a REAR-vs-REAR-RE-ENTER priority rule, and the exemption/`_milestone_blocked` live-buy fix, §4/§5a/§12). **Core constants:** `THRESH = 0.20` (main qualifying threshold for SL/breakout/RED conditions), `ANY = 0.01` (minimum move for "any higher high" pre-RED-family qualification).

**Structure hierarchy:** TZ GREEN → RED → TZ BUY/NEW TZ BUY → RED1 → RED2 → BAR (multi-lineage) → BAR SL → BAR SL2 → REAR → REAR SL → REAR RE-ENTER → REAR RE-ENTER SL.

## 1. TZ GREEN(n)

- Forms on breakout: Low ≥ PrevLow, High > PrevHigh by ≥ 0.20, Close ≥ PrevHigh.
- HH: before RED, any higher High ≥ 0.01 qualifies. After RED, weak rule — qualifies if (diff < 0.20) OR (Low < PrevLow) OR (Close < ref_high_at_red).
- LL: symmetric down-side tracking, standard gap/reclaim logic (gap ≥ 0.20 AND Close doesn't reclaim → new LL; gap < 0.20 → also just an LL update).
- SL (= "INVALID TZ GREEN"): Low breaks ref_low by ≥ 0.20, Close doesn't reclaim → **terminates the entire parent cycle + all descendant structures + all later-created branches**, permanently (`pc.active = False`, never reset). This check runs first each candle and **returns immediately** — TZ BUY-level processing for that branch never even runs the same day TZ GREEN SL fires (TZ GREEN SL always wins any same-day conflict with TZ BUY SL).
- RED(n) has no "INVALID" event in the 37-event list — once RED fires it is **permanent** for that TZ GREEN cycle (unlike RED1, which can be invalidated). No dormancy, no termination of its own.
- **Display rule:** TZ GREEN HH keeps updating internally forever, but is only **shown** while no buy (TZ BUY/NEW TZ BUY) is currently live for this branch. It reappears once the buy stops being live. (TZ GREEN SL/LL are not subject to this — they're structurally impossible while a buy is live in the same way, since TZ BUY's presence doesn't gate the TZ GREEN SL check itself.)
- **TZ-GREEN-specific: HH suppressed on its own SL day.** If a candle satisfies both TZ GREEN HH and TZ GREEN SL conditions simultaneously, only SL is shown — the cycle terminates entirely that same candle, so the HH is moot. This is **only** for TZ GREEN (confirmed by the user explicitly) — BAR, TZ BUY, REAR, and REAR RE-ENTER all keep showing HH alongside their own SL on the same day; their SL does not retroactively erase that day's HH the way TZ GREEN's does.

### 1a. Reference-high inheritance across branches (dormant ancestor ← current leader)

- The AFTER-RED weak rule (§1's HH rule) governs whether a post-RED higher high is *displayed* as `TZ GREEN HH(n)` and, for the currently-active branch, what a *fresh* TZ BUY has to clear — it is **not** a ceiling on what a dormant older branch is allowed to know about. A branch's reference high is, at bottom, "highest High ever confirmed for this cycle, unless terminated" — RED/TZ BUY/BAR/REAR status governs *display* and *TZ-BUY-formation strength*, not whether the number itself is allowed to climb.
- Concretely: whenever exactly **one** branch is currently non-dormant (the "leader") and one or more older branches are dormant (not terminated) alongside it, every dormant branch's `ref_high` is raised to match the leader's `ref_high` whenever the leader's is higher — including advances the leader made at TZ BUY level (already folded into the leader's own `ref_high` via the pre-existing §11 buy-sync). This runs once per candle, after that candle's own per-branch evaluation and the leadership contest, so it includes the leader's same-day advance with the same one-day lag inherent in §11's own buy→parent sync (the leader's TZ-BUY-level gain on day D shows up in the leader's own `pc.ref_high` on day D+1, so the dormant ancestor's inherited value follows on D+1 too).
- When there are **zero or multiple** non-dormant active branches (e.g. everyone resets to non-dormant because no buy is live anywhere system-wide), there is no single leader to inherit from — every branch reverts to tracking independently off raw price data, same as before this rule.
- This is a ratchet like every other reference-high: once inherited, it never falls back down even if the leader that supplied it subsequently fails (SL, deep-failure, etc.) — only that dormant branch's *own* SL removes it from play.
- **Confirmed 2024 dataset, 21–23/01/2024:** TZ GREEN(A) dormant under TZ GREEN(B) (from 17/01). TZ BUY(B) reaches 306.0 via `TZ BUY HH(B)` on 22/01 → B's own `pc.ref_high` picks that up on 23/01 (one-day lag, §11) → A's `ref_high` inherits 306.0 that same day (23/01), even though A's own local weak-rule check on 23/01's candle alone would only have reached 305.25. Confirmed by the user: A's reference high on 22/01 is 305.0 (unmoved, pre-lag), on 23/01 is 306.0 (inherited).
- **Downstream ripple, same dataset, 30–31/01/2024:** A's `ref_high` stays at 306.0 (ratchet) even after B's subsequent TZ BUY SL (24/01) and TZ GREEN SL (26/01). When B reforms and A independently resumes its own tracking (no live buy anywhere resets both to non-dormant, 25/01), A's own future TZ BUY must now clear 306.0 + 0.20, not the lower 305.25 it would have needed without this rule. Result: `TZ BUY(A)` — which forms on the first candle whose High decisively clears the inherited 306.0 — moves from 30/01 (H=306.0 exactly, does not clear) to 31/01 (H=308.0, clears). Because a fresh TZ BUY milestone unconditionally terminates any newer sibling the same day it fires (no continuation-exemption for fresh buys), B's own `TZ GREEN HH(B)` — which used to be wiped as collateral damage when TZ BUY(A) fired on 30/01 — now survives and displays on 30/01, since TZ BUY(A) no longer fires that day. Confirmed correct by the user.

## 2. TZ BUY(n) / NEW TZ BUY(n)

- First-time TZ BUY: after RED, High > TZ GREEN's reference (whichever is higher, before or after RED) by ≥ 0.20, Low ≥ PrevLow, Close ≥ that reference.
- NEW TZ BUY (retry): same shape, but reference = the **old, now-dead buy's own peak**, not TZ GREEN's.
- TZ GREEN remains an independent active structure once TZ BUY forms (not dormant) — but its HH display is suppressed as above.
- TZ BUY HH/LL: same AFTER-RED1 weak-qualification pattern as TZ GREEN, using the buy's own `red1_since`/`ref_high_at_red1`.
- TZ BUY SL: Low breaks buy's ref_low by ≥ 0.20, Close doesn't reclaim → `buy.active = False`, **permanent** (write-once; recovery only via a brand-new `Buy()` object = NEW TZ BUY). Also cancels `bar_pending` and discards any in-flight `buy.red1` at this point (added this session — every other terminal SL already did this, top-level SL was the one gap).
- TZ BUY SL does **not** stop the BAR/REAR family below it — that keeps racing independently once formed.
- **Top-level HH suppression:** once a BAR lineage OR a REAR/REAR RE-ENTER object has **ever** been created for this buy (regardless of current dormant state), the top-level buy's own HH tracking is suppressed **permanently** — the only way back to a front-facing top-level display is via that same buy's own SL and a fresh NEW TZ BUY retry. (Must NOT be conditioned on "currently non-dormant" — that was a real bug this session: a dormant-but-not-yet-superseded REAR/REAR RE-ENTER let stale top-level HH leak back through.)
- **System-wide rule:** only one TZ BUY/NEW TZ BUY may be "live" anywhere at a time — see §6 (`_buy_currently_live`).

## 3. RED1(n) / RED2(n) — shared mechanic across buy/BAR/REAR/REAR RE-ENTER

- Fresh RED1 attaches when: High ≤ PrevHigh, Low < PrevLow by ≥ 0.20, Close ≤ PrevLow. Only **one** RED1 can be in-flight system-wide at a time (`buy.red1`, a single shared tracker, regardless of which stage it's attached to).
- RED1 HH: further High within the pullback, any amount above `red1.ref_high`.
- RED1 LL: Low breaks `red1.ref_low` but the full RED2 conjunction does not hold.
- RED2: Low breaks `red1.ref_low` **AND** High ≤ PrevDayHigh **AND** gap ≥ 0.20 **AND** Close ≤ `red1.ref_low + eps` — all four together.
- INVALID RED1: High clears `red1.ref_high` by ≥ 0.20 with Close holding above → `red1.active = False`, and resets the **parent structure's own HH regime** back to the simple/strict pre-RED1 rule (not stuck on the weak rule forever).
- RED1/RED2 cannot repeat on the same stage object once its own RED2 has fired once (`red2_ever` for BAR lineages; dormancy/`bar_pending` routing naturally blocks re-attachment for buy/REAR/REAR RE-ENTER).
- RED2 sets `buy.bar_pending = True` ("a fresh BAR is now awaited") and, if it fired from REAR's or REAR RE-ENTER's own RED1, sets that structure `.dormant = True`.
- **SL always beats RED1/RED2** (established this session, applies uniformly): every stage's own SL condition is checked **first**, every candle, before any RED1/RED2 processing. If SL fires, RED1/RED2 is skipped entirely that candle — no attach, no continuation, no resolution — regardless of whether RED1 was already in-flight from an earlier day or would be freshly attaching today.
- **Structural invariant:** an HH-type event (TZ GREEN HH / TZ BUY HH / BAR HH / REAR HH / REAR RE-ENTER HH) can never legitimately co-occur with a RED-family event (RED/RED1/RED2) for the *same* structure on the *same* candle — HH requires High > reference; RED-family requires High ≤ PrevHigh; under correct tracking the reference is never below PrevHigh. If this combination ever appears, it signals a stale/lagging reference bug, not a valid state.

## 4. BAR(n) — multi-lineage family

- **Formation mechanism 1:** `bar_pending` consumed by a general breakout (Low ≥ PrevLow, High > PrevHigh by ≥ 0.20, Close ≥ PrevHigh) → forms a brand-new lineage (`n.k`). Removes any lineage still fully pre-SL or dormant/invalidated; **keeps** any lineage actively racing toward its own SL2.
- **Formation mechanism 2:** branches directly off the *newest* lineage's own SL range (same breakout shape, and today's High/Low fall within `[sl.ref_low, sl.ref_high]`) — does **not** remove the older lineage; both coexist and race independently ("multi-generation racing").
- BAR HH: shown for as long as the lineage exists at all (even post-SL — feeds `bar_high_pool`/REAR's reference), AFTER-RED1 weak rule once `red1_since = True`.
- BAR LL: only shown pre-SL; once SL exists, BAR SL's own LL takes over that role.
- BAR SL: Low breaks the lineage's ref_low by ≥ 0.20, Close doesn't reclaim. On formation: `buy.red1 = None`, `lin.red1_since = False` (revert BAR HH's ongoing regime to the simple rule — no active BAR left to protect the weak-rule anchor).
- Post-SL, pre-SL2, every candle checks (in this priority order): **INVALID BAR SL first** (High clears `sl.ref_high` by ≥ 0.20, Close holds) — if it fires and this is the newest lineage and today independently satisfies the entry-shape formula → **reactivates as a fresh BAR(n) under the same label**; if it fires but doesn't qualify for reactivation → goes **dormant** (`sl.invalidated = True`, tracks only INVALID BAR LL from here); if it fires but a newer lineage already exists beyond this one → **terminates outright**, label freed. Then BAR SL HH / BAR SL LL (ordinary tracking). Then BAR SL2.
- **Reactivation is a genuinely fresh BAR cycle in every respect except the label** ("as good as a new bar, only naming notation" — user's framing). It reuses the *same* `BarLineage` Python object (not a new one), so the reactivation code must explicitly reset every field that a truly-new lineage would start fresh with: `sl = None`, `ref_high`/`ref_low` = today's H/L, `red1_since = False`, **and `red2_ever = False`** — this last one was a real, severe bug (see §12): a `red2_ever` baked in from the lineage's *pre-reactivation* life permanently blocked all future RED1/RED2/BAR-reformation on that lineage, cascading into blocking most of the rest of the dataset. (`ref_high_at_red1` does *not* need resetting — it's only ever read while `red1_since` is `True`, which is reset to `False` here, and gets freshly overwritten the instant a new RED1 actually attaches — so leaving it alone is correct, not an oversight.)
- **Reactivation also cancels `buy.bar_pending` outright**, not just for today. Reactivation *is* the fresh BAR that `bar_pending` was awaiting (just under the same label instead of a new one). Leaving the flag merely blocked-for-one-day let it fire again the very next candle via mechanism 1 and repeatedly relabel/wipe the same continuing lineage (A.2 → A.3 → A.4 → ...) on every later breakout candle, discarding real history each time.
- **Same-candle single-BAR rule:** only one BAR can exist or form per candle. A lineage reactivating via its own INVALID BAR SL must not be silently wiped by mechanism 1 (the general `bar_pending`-driven breakout check, evaluated after the per-lineage loop) also firing the *same* candle — that would print the reactivation event and then immediately discard the reactivated object when mechanism 1's own filter rebuilds `bar_lineages`. Guarded via a `reactivated_this_candle` flag set the instant any lineage reactivates, which gates mechanism 1 off for that candle ("the currently active cycle wins" — user's framing).
- BAR SL2: Low breaks `sl.ref_low` (or latest SL LL) by ≥ 0.20, Close doesn't reclaim. **Permanent, one-way.**
- Dormant/invalidated lineages: no more HH/SL-HH/SL2 tracking — only Low-side INVALID BAR LL, unless a fresh Low breach *also* independently re-qualifies as a full fresh BAR SL(n), which takes priority and re-arms the SL cycle from scratch on a brand-new `BarSL` object.
- **BAR SL2 terminates every other open BAR SL, same day or not** (established this session): the moment any lineage's SL2 confirms, every *other* lineage still sitting in an open (pre-SL2) BAR SL — whether that SL formed earlier or on this very same candle — is terminated: its **entire today's contribution is wiped** (not shown at all, not merely blocked going forward), and it's permanently removed from tracking. A lineage still fully pre-SL, or already past its own SL2, is unaffected.
- **REAR reference at SL2 formation** (refined this session — Event028): `sl.invalid_hh_ref = max(lin.ref_high, sl.ref_high)` using **only the winning lineage's own peak**, UNLESS that same lineage's SL cycle showed its **own** INVALID BAR SL at least once before reaching SL2 — only then does the wider cross-generation `buy.bar_high_pool` apply: `max(bar_high_pool, lin.ref_high, sl.ref_high)`. A sibling lineage's peak from its own separate life, never reconfirmed by *this* lineage's own recovery, does not transfer over.
- At SL2 formation, `buy.bar_pending` is cancelled (the awaiting-fresh-BAR flag from this lineage's own earlier RED2, if any).

## 5. REAR(n)

- Forms when, on a lineage already at SL2, price recovers above `sl.invalid_hh_ref` by ≥ 0.20 (Low ≥ PrevLow, Close ≥ that reference). **First lineage to achieve this wins** — REAR forms off its reference, and **every other lineage (ancestor or descendant) terminates immediately**, `buy.bar_lineages = []`, `buy.rear_reenter = None` (single-slot: newest REAR-family formation always wipes an older dormant one).
- Before winning (or while blocked by the leadership contest), a partial breakout just updates `invalid_hh_ref` and shows INVALID BAR HH — REAR never "happens and immediately fails," it stays queued.
- REAR HH/LL: ordinary tracking pre-SL, AFTER-RED1 weak rule once `red1_since`.
- **REAR's own SL is checked first every candle, unconditionally, regardless of dormant state** (own-RED2 exhaustion doesn't stop the market — a real SL breach must still take effect). On formation: `buy.bar_lineages = []`, `buy.bar_sub_counter = 0`, `buy.red1 = None`, `buy.bar_pending = False` (BAR is not a valid next event once REAR SL exists — per Event031, only REAR RE-ENTER/INVALID REAR HH are).
- Once REAR has its own SL (dormant or not), Event031's rules (INVALID REAR HH / REAR RE-ENTER) run **unconditionally** — dormancy stops mattering entirely from that point.
- **REAR RE-ENTER forming makes REAR permanently retired.** `buy.rear` must never be examined again for anything once `buy.rear_reenter` exists in *any* form (dormant or not, SL'd or not) — this must be an explicit code guard, never an assumption based on other code's ordering.

### 5a. REAR-family recovery from a LATER BAR's own SL2 (established after repeated errors this round — see §12 postmortem)

A fresh BAR can form again *after* REAR/REAR RE-ENTER already exists, whenever that ancestor's own RED2 fires and a new BAR generation confirms underneath it (dormant, per §7b). When *that* BAR later reaches its own SL2 and recovers, there are exactly two possible outcomes, checked in this fixed priority order every candle:

1. **Reactivating the ancestor in place, under its own identity** (`REAR RE-ENTER(n)` if `buy.rear_reenter` exists, else `REAR(n)`) — using the **ancestor's own** frozen reference (`target.ref_high`, tracked silently the whole time it's been dormant, per §7b). The ancestor has existed since *before* this BAR cycle started, so it wins whenever its own reference clears, **even if the BAR's own SL2 reference ALSO clears the same candle** (21/06/2022 — confirmed: both references happened to be numerically identical, 451, on the same candle; REAR RE-ENTER, having started first, reactivates in place — `buy.rear_reenter` is *not* wiped).
2. **Only if (1) doesn't apply** (ancestor's own reference not cleared that day): a **fresh** `REAR(n)`, using *only* the BAR's own Event028 reference (`sl.invalid_hh_ref`, computed at that BAR's own SL2 exactly as in §4) — this is the *same* mechanism as a first-ever REAR, and it wipes any still-existing dormant `rear_reenter` (single-slot rule, §5) since its own condition wasn't met (04/07/2022 — confirmed: BAR's own reference of 457 cleared, but REAR RE-ENTER's own separate, higher reference of 458.95 — re-established after its 21/06 reactivation — had not; REAR RE-ENTER cannot occur that day at all, only the fresh REAR).

**Implementation pitfall (found and fixed after the 21/06/2022 case was re-flagged):** the ancestor's reference (`target.ref_high`) must be read **as it stood coming into today**, not read live after today's own dormant HH tracking (§7b) has already run. `_eval_buy` evaluates the ancestor's dormant HH/LL tracking (§7b's "simple rule while dormant") *before* routing to this reactivation check — so on a candle where the ancestor's own simple-rule HH and the BAR's SL2-recovery threshold are the exact same number, the dormant tracker silently bumps `target.ref_high` to today's own High first, and the reactivation check then compares today's High against *itself* (always fails, `cur.h > ancestor_ref` is never true against an equal value) — the fresh-REAR path (case 2) wins by default even though case 1 should have. Fixed by snapshotting `target.ref_high` at the very top of `_eval_buy`, before the dormant HH tracking runs, and threading that pre-today value into `_eval_bar_lineages_progress` for this specific comparison — the ancestor's own tracker still keeps updating live (§7b unaffected), only the reactivation-priority comparison uses the frozen pre-candle value. Verified: 21/06/2022 now correctly fires `REAR RE-ENTER(A)` (not `REAR(A)`); 04/07/2022's fresh-REAR case (point 2 above) is unaffected.

**"REAR" is not a one-time-per-buy milestone** — it recurs every time a BAR reaches SL2 and recovers on its own reference, *even while inside an ongoing REAR RE-ENTER cycle*, as long as the current ancestor hasn't itself failed at its own SL. **The only thing that blocks it entirely** is an ancestor that has *already* been decisively terminated via its own SL (26/04/2022 — REAR's own SL fired the same day as a BAR's SL2; from that point on the only valid paths back up are that same REAR's own REAR RE-ENTER machinery, or an entirely new TZ GREEN branch reaching its own TZ BUY — never a fresh REAR "above the recent BAR reference high"). Implemented as `_rear_ancestor_terminated(buy)`: True only when the current ancestor (`rear_reenter` if it exists, else `rear`) has `sl is not None`.

Field-reset discipline on reactivation (case 1) is identical to every other reactivation in this file (§12a): `ref_high`/`ref_low` = today's H/L, `red1_since = False`, `dormant = False`, `red2_ever = False` explicitly reset; `ref_high_at_red1` left alone (dead while `red1_since` is `False`, freshly overwritten on next RED1 attach).

## 6. REAR RE-ENTER(n)

- HH/LL: ordinary tracking, AFTER-RED1 weak rule, own SL checked first every candle regardless of dormant (same principle as REAR).
- Own SL: Low breaks ref_low by ≥ 0.20, Close doesn't reclaim → `buy.red1 = None`, `buy.bar_pending = False`.
- Post-SL, reactivation ("REAR RE-ENTER(n)" again, same event text) fires if price recovers above `sl.invalid_hh_ref` by ≥ 0.20 with Low ≥ PrevLow: resets `sl = None`, `ref_high`/`ref_low` to today's H/L, `red1_since = False`, **and `dormant = False`** — this reset is mandatory; forgetting it leaves the structure permanently unable to track HH or attach RED1/RED2 again even though it's technically "reactivated" (a real bug found and fixed this session).
- If reactivation doesn't qualify → INVALID REAR RE-ENTER HH tracking (reference climbs, no live position).
- No RED1 possible here — REAR RE-ENTER is the deepest, terminal leaf of the entire 37-event hierarchy.

## 7. Dormancy — the general principle (source of most bugs this session)

Two **separate** mechanisms share the word "dormant":

### 7a. Branch-level (`pc.dormant`) — Leadership Contest
- Whenever any branch achieves a milestone (TZ BUY(/NEW TZ BUY(/BAR(/REAR(/REAR RE-ENTER( formation), every *other* active branch is judged: older (lower seq) → **dormant**; newer (higher seq) → **terminated outright** (unless exempted).
- **Exemption:** a *continuation* milestone (BAR/REAR/REAR RE-ENTER — NOT a fresh TZ BUY/NEW TZ BUY) cannot terminate a newer branch that already held an active buy **before today** (checked via a pre-today snapshot taken at the start of `process()`, not post-processing state — a same-day tie goes to the older/earlier-queued cycle).
- Dormancy lifts automatically the instant no branch anywhere holds a live buy — not gated on the dormant branch producing a fresh milestone first.
- **Display rule:** a dormant branch computes everything normally in the backend every candle (all references keep updating) but only shows: the 5 milestone-formation events, **and** SL/LL-type events (real, decisive price breaches — TZ GREEN/TZ BUY/BAR/REAR/REAR RE-ENTER SL and LL, including BAR SL2). HH-type events, the whole RED-family (RED/RED1/RED2/RED1 HH/RED1 LL/INVALID RED1), and "INVALID … HH"-style recovery events stay suppressed while dormant. A milestone firing while dormant also lifts dormancy going forward.

### 7b. Stage-level (`buy.rear.dormant` / `buy.rear_reenter.dormant`) — RED2 exhaustion or supersession
- Set True when: (a) that structure's *own* RED2 fires while still pre-SL ("awaiting a fresh BAR instead"), or (b) REAR is permanently superseded the instant REAR RE-ENTER forms.
- **Only ever meaningful while `sl is None`.** The moment that structure has its own SL — however it got there — dormant becomes irrelevant; Event031/036's rules govern unconditionally from then on. Every read *and* write of `.dormant` must be gated behind `sl is None`; a write while `sl is not None` should never happen (add explicit guards, don't rely on it being a harmless no-op elsewhere).
- While dormant and `sl is None`: SL is still checked and takes effect (and cancels `bar_pending` if it fires); LL still shows; HH is suppressed (backend still tracks the reference silently); RED1/RED2 do not attach.
- **Routing pitfall (hit twice this session):** a catch-all like `elif buy.rear_reenter is not None: pass`, meant only to block falling back to the now-irrelevant `buy.rear`, will *also* block the legitimate fallthrough to `bar_lineages`/`bar_pending` checking if it consumes the whole elif slot. Any such guard must be scoped precisely — exclude only what it's meant to exclude, nothing else.

## 8. Branch spawning eligibility (new sibling TZ GREEN)

- Eligible when: a "tip" anchor exists (the single newest active branch), its own RED has fired, it's not dormant, **and** its buy is either nonexistent, or top-level-dead, or has reached "deep failure" (BAR SL2 on any lineage / REAR SL / REAR RE-ENTER SL, ever) **and is not currently live right now** (refined this session — historical deep-failure alone is not enough if the same buy has since recovered and is actively live again, e.g. via REAR RE-ENTER currently climbing).
- Spawn breakout shape is identical to BAR's entry-shape formula.
- `_deep_failure_reached` is historical (never un-sets once true). `_buy_currently_live` is **not** historical — it re-evaluates live status every candle, including flipping back to "live" if REAR RE-ENTER later reactivates a previously-failed buy.

## 9. `_buy_currently_live` (system-wide "only one buy live" rule)

1. `False` if `buy.active` is `False` (top-level SL'd — permanent).
2. If `buy.rear_reenter` exists: SL not `None` → `False` (decisive, regardless of dormant). SL `None` and not dormant → `True`. SL `None` and dormant → fall through to bar_lineages (superseded, awaiting fresh BAR).
3. Else if `buy.rear` exists: same pattern.
4. Else if `buy.bar_lineages` non-empty: `True` if *any* lineage still has `sl is None` or (`sl` exists but not yet `sl2`) — live as long as anything is still unresolved.
5. Else: `True` (nothing has failed yet).

## 10. Cross-generation reference pool (`buy.bar_high_pool`)

- Monotonically increasing max, fed by: every BAR HH (formation or ongoing), every BAR SL HH, every INVALID BAR SL recovery high, every INVALID BAR HH.
- Used for: (a) TZ BUY's own top-level reference sync (never falls behind what the BAR family has proven), and (b) — gated by `sl.ever_invalid` (see §4) — REAR's reference at SL2 formation.

## 11. Cross-level reference sync

- `pc.ref_high` (TZ GREEN) is synced up to `pc.buy.ref_high` every candle whenever the latter is higher — this sync runs *before* that candle's own buy-level HH computation, so there's an inherent one-day lag. Harmless only because TZ GREEN HH stays display-suppressed the entire time a buy is live (§1).
- `buy.ref_high` (TZ BUY) is synced up to `buy.bar_high_pool` whenever the latter is higher.
- **`bar_high_pool` must NEVER be synced into `buy.rear.ref_high` / `buy.rear_reenter.ref_high` — a real, briefly-shipped bug, reverted.** `bar_high_pool` is a *blind*, unconditional cross-generation max — it pools peaks from sibling BAR lineages that may have since been terminated and are structurally ineligible to matter again (§4's Event028 rule: a sibling lineage's peak only pools into REAR's reference when *this* lineage showed its own INVALID BAR SL; otherwise REAR uses *only* this lineage's own peak, deliberately excluding a higher-but-unrelated sibling peak). Syncing REAR's own reference to `bar_high_pool` silently reintroduces exactly the pooling Event028 says NOT to do (confirmed wrong with real numbers: 2024 dataset, `BAR(B.2)` reached SL2 with its own, lower reference while sibling `BAR(B.1)`'s higher, terminated peak sat in `bar_high_pool` — syncing to the pool would have inflated `REAR(B)`'s reference with B.1's ineligible peak). `bar_high_pool`'s only legitimate consumer for a top-level reference is `buy.ref_high` (TZ BUY, above) — REAR/REAR RE-ENTER never read it directly.
- **The real fix for "REAR's own reference falls behind a peak already proven while dormant" lives in REAR's own HH tracking, not in a cross-reference sync.** `_eval_rear_hh_ll` / `_eval_rear_reenter_hh_ll` gate their weak AFTER-RED1 rule on `red1_since` — but that weak rule exists to filter a shallow bounce from a genuine breakout for a *live* structure currently being evaluated for real trading decisions. Once dormant (superseded), REAR is a backend-only tracker; its `ref_high_at_red1` anchor is frozen from *before* it went dormant and has nothing to do with the market now. The fix: the simple "any higher high ≥ 0.01" rule applies whenever `not red1_since` **or `dormant`** — not just `not red1_since`. Confirmed with real numbers: REAR(A) formed 24/03/2025, went dormant 04/04; on 16/04 `cur.h=251` genuinely exceeded its then-current reference of 244.25 by more than enough, but the weak rule's stale anchor (237, frozen from before dormancy) blocked the update since none of its three conditions happened to hold that exact candle. With the `dormant` gate added, 16/04 correctly records the true peak (251) under REAR's *own* tracking — no cross-structure borrowing needed, and Event028's pooling rule for fresh REAR formation stays untouched.

## 12. Testing & verification discipline

- **Never guess.** Verify every claim against actual OHLC numbers before agreeing or disagreeing with any flagged date.
- After every fix: re-run against **all** previously-validated datasets (not just the one being looked at) and diff the full output — zero unexpected changes required before delivering anything.
- **Anomaly scan:** no buy should ever have 2+ simultaneously open (`sl is None`) `bar_lineages`.
- **Before treating any state-flag fix as done (per-flag audit):** (1) list every place in the file that reads or writes that flag, (2) state the correct behavior at each site independent of what the code currently does, (3) confirm the change makes all of them consistent with each other — not just the one the failing date exposed, (4) re-run and diff against every already-validated dataset.
- **Per-flag audit is necessary but NOT sufficient — always also run a per-transition audit (added after the `red2_ever` incident, §12a below).** A flag can pass every per-flag check (write-once, never contradicted at its own sites) and still be wrong, if some *other* piece of code resets the object it lives on without knowing that flag exists. Per-flag asks "is this flag's own life story internally consistent?" Per-transition asks "at this specific reset/reactivation point, for *every* field on this object, was reset-vs-keep explicitly decided?" — only the second question catches a flag nobody thought to ask about at the transition site.
- Prefer explicit, local guards over implicit safety that depends on some other part of the file staying in a particular order — several bugs this session came from exactly that pattern (a flag was "safe" only because of an assumption elsewhere that later broke).
- **Postmortem — "which of two structurally-similar mechanisms wins" needs an explicit priority rule, not analogy.** §5a's rule (REAR-family reactivation vs. a fresh REAR, off a later BAR's own SL2) took three wrong attempts before landing correctly: first, silently dropping the event entirely; then guessing the wrong reference field; then guessing the wrong event identity. The fix each time came only from the user supplying the exact numbers and the exact priority ("whichever occurred earlier wins") — not from reasoning by analogy to a superficially similar, already-established rule. **When two established mechanisms could both plausibly apply to the same event, do not infer priority from pattern-matching — verify both candidates' own numbers independently and ask which one is meant to win, or find the explicit priority rule already on record, before writing the fix.**

### 12a. Per-transition audit methodology (mandatory for any fix that resets/reuses an existing object)

Triggered by the `red2_ever` incident: `BarLineage.red2_ever` passed its own per-flag audit cleanly (write-once, read-once, internally consistent) — the gap was that the *reactivation* transition (which already reset `sl`/`ref_high`/`ref_low`/`red1_since`) was never cross-checked against `red2_ever`, because nothing about auditing the flag's own sites points you at every transition elsewhere in the file that might reset the object it lives on.

**The corrected procedure, whenever a fix touches a place that resets/reuses an existing object in place** (as opposed to constructing a brand-new one — a fresh `SomeClass(...)` construction is safe by construction and doesn't need this):
1. Find the dataclass the object belongs to and list **every field on it**, not just the ones the current fix already touches.
2. At the specific reset/reactivation code site, go field by field and explicitly decide reset-vs-keep for each one, stating *why* — "kept because X still means the same thing post-reset" or "reset because a truly-fresh object would start here."
3. For any field left un-reset, trace its only read site(s) and confirm they're provably gated behind some *other* condition that the transition already resets (e.g. `ref_high_at_red1` is dead whenever `red1_since` is `False`) — don't leave a field un-reset on the assumption alone.
4. Re-run and diff against every already-validated dataset, same as the per-flag procedure.

**Known reset-in-place transitions in the current file (audited under this procedure, as of this fix):**
- `BarLineage` reactivation (§4): `sl`, `ref_high`, `ref_low`, `red1_since`, `red2_ever` reset; `ref_high_at_red1` provably dead until next RED1 attach (left alone, correctly); `label` kept by design.
- `RearReenter` reactivation (§6): `sl`, `ref_high`, `ref_low`, `red1_since`, `dormant` reset; `ref_high_at_red1` provably dead, same reasoning; has no `red2_ever`-equivalent field, so no sibling bug is possible there.
- REAR/REAR RE-ENTER-ancestor reactivation off a later BAR's own SL2 (§5a): same object, same field-reset list as `RearReenter` reactivation above (`ref_high`, `ref_low`, `red1_since`, `dormant`, `red2_ever`) — this is the same transition, just triggered from a different call site (a child BAR's own SL2 recovering, not the ancestor's own SL breach). This class of transition took multiple wrong attempts this round (see the postmortem note below) before landing on the correct priority rule.
- Everything else that looks like a "restart" — `Rear(...)` forming, `RearReenter(...)` first forming, a dormant BAR SL re-arming into a fresh `BarSL(...)`, a new `ParentCycle(...)` spawning — constructs a **brand-new object**, not a reuse. Safe by construction; no per-transition audit needed there, only per-flag.
- `pc.dormant = False` (branch-level dormancy clearing) is intentionally *not* a "start fresh" transition — the code's own intent is "resume as-is," so nothing else on `ParentCycle` is meant to reset there.

When a future fix adds a new reset-in-place transition, or a new field to `BarLineage`/`RearReenter`, redo this table entry for that class.
